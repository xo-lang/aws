# 0002: The code generator, written in Xo, from AWS's Smithy JSON models

Status: Proposed (Xo AWS 1, 2026-11-04)

## Context

aws-sdk-go-v2 is generated by smithy-go's Java codegen plugin from the
Smithy models AWS publishes. AWS now publishes the same models as Smithy
JSON AST files in github.com/aws/api-models-aws (Apache-2.0), one file per
service and version (`models/<service>/service/<version>/<service>-<version>.json`).
The JSON AST holds every shape, its traits (protocol, auth, endpoint rule
set and its tests, pagination, waiters, documentation, HTTP bindings,
idempotency tokens, checksums, event streams), so a generator needs no
Smithy IDL parser and no Java to read service models.

The owner decided the generator is written in Xo.

## Decision

### Inputs and pinning

- `codegen/models.lock` pins the api-models-aws commit (full SHA) and the
  SHA-256 of each model file the generator reads. `codegen/fetch-models.sh`
  clones that commit into a gitignored cache (`codegen/.models/`), checks
  the hashes, and fails on any mismatch. The model files are not committed
  (hundreds of MB); the commit pin plus the committed output make each
  generation reproducible.
- Partitions (`partitions.json`, the region and partition table the
  endpoint rules' `aws.partition` function reads) come from the same
  source aws-sdk-go-v2 uses (its `internal/endpoints/awsrulesfn`
  partitions file, Apache-2.0), pinned the same way and embedded in the
  core with `embed(...)` (spec 3.1, decision 0304 of Xo).
- `NOTICE` names api-models-aws and the partitions source with their
  Apache-2.0 attribution; `codegen/LICENSE-models` keeps the license text.
  Generated files carry a header: `// Code generated by xo-lang/aws
  codegen from <sdkId> <model version> (api-models-aws <short SHA>). DO NOT
  EDIT.`

### Pipeline

```
model JSON  ->  load (std/json Value)  ->  resolve (prelude, mixins,
apply, targets)  ->  index (shapes by id, operations, closure of shapes
each service reaches)  ->  plan (names, nullability, protocol, auth,
endpoints, paginators, waiters)  ->  emit Xo text  ->  xo fmt  ->  write
```

1. **Load and resolve.** Parse with `json.parse_value`. Resolve `apply`
   blocks and mixins (the AST ships them flattened for AWS models, but the
   generator checks and fails rather than guessing), and the Smithy
   prelude shapes (`smithy.api#String`, ...) from a small embedded table.
2. **Plan.** Every name decision is made once here and recorded in a
   plan structure that the emitter only reads, so naming rules are tested
   without emitting code:
   - Types and enum variants: `UpperCamel` (XO0101); struct fields and
     functions: `snake_case`, converted from the member name by the
     word splitting in the open item below (`BucketName` is
     `bucket_name`).
   - Collisions after conversion (two members mapping to one field, a
     shape named like a generated helper, a field named like a keyword such
     as `type` or `match`) get a deterministic suffix (`type_`), and every
     such rename is listed in a generated `RENAMES.md` per service so a
     user can look one up.
   - Wire names stay exact: the member name, `jsonName`, `xmlName`,
     `httpHeader`, `httpQuery`, `httpLabel`, `ec2QueryName` traits are
     carried as strings into the serializers.
3. **Emit.** One package per service, files split by role so no file is
   enormous: `client.xo` (client, options, constructor), `api_<op>.xo` per
   operation (input, output, the operation method, its middleware
   registration), `types.xo` and `types_<n>.xo` (shapes), `enums.xo`,
   `errors.xo`, `serializers.xo`/`deserializers.xo` (per protocol),
   `endpoints.xo` (the compiled rule set), `endpoints_test.xo` (the
   model's endpoint tests), `paginators.xo`, `waiters.xo`, and
   `doc.xo` (package documentation). Files are then run through `xo fmt`.
4. **Check.** The generator's own test runs `xo check` on every emitted
   service it touched; a type error in generated code is a generator bug
   and fails the generation.

### Serializers are generated, not derived

Generated shapes do not use `derive Json` or `derive Xml`. AWS protocols
need rules the derives do not have: timestamps as epoch seconds, ISO 8601
or HTTP dates per member and per protocol; `NaN` and `Infinity` as
strings; blobs as base64 in JSON but raw in payloads; sparse lists and
maps with `null`; unions as one key objects; XML flattened lists, member
names, namespaces and attributes; query protocol's `Member.N` keys. The
emitter writes explicit serialize and deserialize functions per shape,
on top of small hand written codec helpers in the core
(`protocol/restjson`, ...): JSON is written to a `StrBuilder` and read
from `json.Value`; XML is written with `xml.escape_to` and read from the
`xml.parse` tree. A future streaming JSON reader can replace `json.Value`
without changing generated signatures (0006 item 3).

### Endpoint rules are compiled to Xo

Each service's `smithy.rules#endpointRuleSet` becomes straight line Xo
code (conditions to `if let`, `assign` to `let`, functions to calls into
`endpoints/`), as aws-sdk-go-v2 does. The core also keeps a small rules
interpreter used only by tests, to check the compiled code against the
interpreter on the model's `endpointTests`.

### Scale and ordering

- The generator runs per service, so `codegen gen s3` regenerates one
  service, and a full run fans out over services in a `scope` with a
  bounded number of tasks.
- First services, in the owner's order: S3, DynamoDB, SQS, STS, then
  Secrets Manager, SNS, Lambda; then every other model. Each new protocol
  feature is first proven on the protocol test services (0005) before a
  real service relies on it.
- Compiler scale is a risk: EC2's model has about 600 operations and
  several thousand shapes. The generator's first milestone after S3
  generates EC2 and measures `xo check` and `xo build` time and memory
  through the lead's heavy job wrapper; the result decides whether large
  services are split into several packages (0006 item 1).

### Open item

The exact snake case splitting of AWS member names with acronyms
(`SSEKMSKeyId`, `IAMRoleARN`, `DBInstanceIdentifier`) is a choice users
will see everywhere. Proposal: split on lower to upper and on the last
upper of an upper run before a lower (`SSEKMSKey` is `ssekms_key`,
`DBInstance` is `db_instance`, `IAMRoleARN` is `iam_role_arn`), plus a
small override table in the generator for names that split badly. The
first S3 and DynamoDB output will show the result for review before any
service is published.

## Consequences

- Reproducible output from a pinned model commit; committed generated
  code, so users never run the generator.
- The generator is a real Xo program that exercises std/json, files, and
  concurrency at scale; problems it finds go to the xo repository's
  owners (0006).
- Renames are visible and stable: once published, a field name changes
  only with a major version.

## Alternatives

- Use smithy-go's Java codegen with an Xo backend: proven, but needs Java
  and Gradle to generate, and the owner decided the generator is Xo.
- Read the Smithy IDL instead of JSON: needs an IDL parser; the JSON AST is
  published and complete. IDL is needed only for the protocol test models
  (0005), converted once with the Smithy CLI.
- Interpret endpoint rules at run time from embedded JSON: smaller code,
  slower per call, errors found at run time. Kept only as a test oracle.
- `derive Json` and `derive Xml` on generated shapes: less code, but
  wrong for AWS's encodings (above).
